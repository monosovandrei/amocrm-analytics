# Пульт РОПа и активная аналитика amoCRM

## Локальный контур

Продовую БД и продовый сервис во время разработки не трогаем.

Рабочий порядок:

1. Все изменения делаются в локальной копии проекта.
2. amoCRM-данные подтягиваются в локальную БД.
3. Миграции применяются сначала локально.
4. Перед релизом прогоняются тесты, сборки, `frontend:gate` и ручная проверка экрана.
5. Прод обновляется отдельным релизом только после подтверждения готовности.

## Образ результата

`Пульт РОПа` - первый рабочий экран для руководителя продаж. Он не заставляет искать проблему по отчетам, а сразу показывает:

- кто из менеджеров не закрывает день по задачам;
- где есть просроченные действия;
- каким клиентам с отправленным оффером нужно касание сегодня;
- какие письма клиентов ждут ответа;
- какие сделки зависли на этапах по SLA;
- какие CRM-ошибки надо разобрать;
- какие сделки в риске и почему.

Старые отчеты остаются для анализа истории. Пульт РОПа отвечает на вопрос: где нужно вмешаться сейчас.

## Данные

Первая версия использует существующую локальную модель:

- `CrmUser`, `CrmGroup`;
- `Deal`, `Pipeline`, `PipelineStage`;
- `Task`;
- `Note`;
- `CrmEvent`;
- `DealStageHistory`;
- `EmailThreadState`, `EmailThreadDismissal`;
- `QualityRule`, `QualityViolation`;
- `RopStageSlaRule`.

Менеджеры берутся только из активных и видимых amoCRM-учеток. В пульт попадают только два отдела:

- `Продажи`;
- `CSM`.

Остальные группы и пользователи в этом экране не показываются.

## Первый экран

### Фильтры

Фильтры находятся сверху и работают галочками:

| Фильтр | Поведение |
|---|---|
| Отдел | Можно выбрать все, только Продажи, только CSM или оба отдела |
| Группа | Показывает группы внутри выбранных отделов |
| Менеджеры | Позволяет выбрать одного или нескольких менеджеров |

Выбор отдела автоматически ограничивает список групп и менеджеров. Выбор группы автоматически ограничивает список менеджеров.

### Таблицы отделов

Менеджеры показываются двумя отдельными таблицами:

- `Продажи`;
- `CSM`.

Колонки таблицы:

| Колонка | Что означает | Какое решение помогает принять |
|---|---|---|
| Менеджер | Имя и группа | Кого смотреть |
| Статус | Короткий рабочий вывод по строке | С чего начать разбор |
| Задачи сегодня | Выполнено / всего | Успевает ли менеджер закрыть день |
| Просроченные задачи | Открытые задачи с прошедшим сроком | Где надо снять операционную просрочку |
| Письма без ответа | Входящие письма клиентов без ответа по логике раздела `Почта` | Где клиент уже ждет |
| КП без касания | Клиенты с отправленным оффером, у которых касание стоит на сегодня и еще не выполнено | Кому надо написать или позвонить сегодня |
| Рисковые сделки | Сделки с конкретными причинами риска | Какие сделки требуют вмешательства |
| CRM-ошибки | Активные quality-нарушения по сделкам | Где менеджер плохо ведет amoCRM |
| Зависшие сделки | Сделки, которые находятся на этапе дольше настроенного SLA | Где этап тормозит работу |
| Сделки | Открытые сделки и сумма | Базовая нагрузка |

Агрегированные оценки без формулы не используются. В пульте показываются конкретные счетчики и конкретные очереди действий.

## Очереди действий

Очереди находятся под таблицами отделов. Каждая очередь - список конкретных сделок, отсортированный по приоритету.

Типы очередей:

| Очередь | Условие попадания |
|---|---|
| КП без касания | Сделка на офферном этапе, есть открытая задача на сегодня, но сегодня еще нет исходящего касания или закрытия задачи |
| Письма без ответа | Последнее видимое входящее письмо по сделке еще не закрыто ответом или ручным скрытием, логика совпадает с разделом `Почта` |
| Просроченные задачи | Открытая задача по сделке с прошедшим сроком |
| Зависшие сделки | Текущий этап сделки длится больше SLA этого этапа |
| CRM-ошибки | Активное quality-нарушение по сделке |
| Рисковые сделки | Сделка попала хотя бы в одну риск-очередь; причина собирается из конкретных сигналов |

Поля строки очереди:

| Поле | Назначение |
|---|---|
| Срочность | Что смотреть первым |
| Что сделать | Человеческое название проблемы |
| Сделка | Ссылка в amoCRM, если есть внешний ID |
| Менеджер | Ответственный |
| Воронка / этап | Где находится сделка |
| Возраст / срок | Как давно существует проблема |
| Сумма | Финансовый вес сделки |

## Зависания воронки

Блок `Зависания воронки` показывает срез по выбранной воронке и выбранным менеджерам.

Колонки:

| Колонка | Что означает |
|---|---|
| Этап | Название этапа и причина SLA |
| Открыто | Сколько открытых сделок сейчас на этапе |
| Зависло | Сколько сделок превысили SLA |
| Сумма зависших | Денежный вес зависших сделок |
| Средний возраст | Средний возраст открытых сделок на этапе |
| SLA | Текущий порог этапа |
| Первые сделки | Приоритетные сделки со ссылками |

Приоритет сделок внутри этапа строится по срочности и возрасту проблемы. РОП видит не только этап, но и первые сделки для разбора.

## Настройка SLA

SLA задается в блоке `SLA этапов` внутри пульта РОПа.

Правило SLA хранится по паре:

```txt
отдел + этап
```

Поля настройки:

| Поле | Что делает |
|---|---|
| Отдел | Продажи или CSM |
| Этап | Этап и его воронка |
| Открыто | Сколько открытых сделок сейчас подпадает под правило |
| SLA | Включить или отключить правило |
| Дней | Через сколько дней сделка считается зависшей |
| Причина | Текст, который РОП видит в очереди и в срезе воронки |

Если правило отключено, сделки этого отдела на этом этапе не попадают в `Зависшие сделки` по возрасту этапа.

## Backend

Основной endpoint:

```txt
GET /api/v1/platform/rop-dashboard-v2
```

Поддерживаемые query-параметры:

| Параметр | Назначение |
|---|---|
| `departments` | `sales`, `csm` или оба через запятую |
| `groupIds` | одна или несколько групп |
| `managerIds` | один или несколько менеджеров |
| `pipelineId` | выбранная воронка для серверного состояния фильтра |

Endpoint возвращает:

- доступные фильтры;
- отделы с менеджерами;
- очереди действий;
- срез зависаний по этапам;
- список воронок.

Настройки SLA:

```txt
GET /api/v1/settings/rop-stage-sla
PATCH /api/v1/settings/rop-stage-sla
```

`PATCH` доступен администратору и пишет audit-событие.

## Правила расчета

### Активные менеджеры

Менеджер попадает в пульт только если:

1. `CrmUser.isActive = true`;
2. `CrmUser.isVisible = true`;
3. внешний ID пользователя похож на реальный amoCRM ID;
4. группа пользователя относится к `Продажи` или `CSM`;
5. внешний ID группы похож на реальный amoCRM ID.

### КП без касания

Сделка попадает в очередь, если выполнены все условия:

1. сделка открыта;
2. ответственный входит в выбранный отдел/группу/менеджеров;
3. текущий этап похож на отправленный оффер, КП, предложение или счет;
4. по сделке есть открытая задача на сегодня;
5. сегодня еще нет исходящего письма, исходящего касания, общего примечания или закрытой задачи.

### Письма без ответа

Используется та же логика видимости, что в разделе `Почта`:

1. берется последнее входящее письмо по сделке;
2. учитываются ручные скрытия;
3. исключаются закрытые, выигранные, проигранные и удаленные сделки;
4. в пульт попадают только сделки выбранных активных менеджеров Продаж и CSM.

### Зависшие сделки

Возраст сделки на текущем этапе считается от последнего входа в этот этап. Если истории нет, используется дата обновления или создания сделки.

Сделка считается зависшей, если:

```txt
возраст на этапе >= SLA этапа
```

### CRM-ошибки

В пульт попадают не оценки, а активные нарушения из `QualityViolation`:

- правило;
- сообщение;
- сделка;
- менеджер;
- возраст проблемы.

### Рисковые сделки

Риск - это объединение конкретных причин:

- просроченная задача;
- письмо клиента без ответа;
- оффер без касания сегодня;
- превышение SLA этапа;
- активная CRM-ошибка.

В строке риска показывается список причин.

## Frontend

Страница построена как рабочая CRM-аналитика:

1. фильтры;
2. таблицы отделов;
3. очереди действий;
4. зависания воронки;
5. настройка SLA.

Требования к UI:

- без декоративных блоков и дублей;
- только рабочие данные, фильтры, таблицы, действия и статусы;
- русские подписи;
- горизонтальный scroll только внутри широких таблиц;
- loading, empty и error states;
- desktop и mobile должны открываться без поломки layout.

## Локальная проверка

Перед сдачей локально выполняются:

```txt
npm run frontend:gate
npm test --workspace=@amocrm-analytics/api -- --runInBand
npm run typecheck --workspace=@amocrm-analytics/api
npm run build --workspace=@amocrm-analytics/api
npm run build --workspace=@amocrm-analytics/web
git diff --check
```

Дополнительно через браузер сверяется:

- пульт открывается;
- старые непонятные показатели не видны;
- фильтры работают;
- таблицы отделов заполнены;
- очереди содержат конкретные сделки;
- блок SLA виден и редактируется;
- mobile-viewport не дает горизонтальный overflow всей страницы.

## Релизный порядок

На прод выкатываем только отдельным релизом:

1. создать backup;
2. применить миграции на staging или копии БД;
3. собрать API и web;
4. выкатить API;
5. выкатить web;
6. сверить healthcheck;
7. сверить авторизацию;
8. сверить старые разделы: отчеты, план-факт, SLA лидов, почта;
9. сверить `Пульт РОПа`.

## Что не делаем в первой версии

- Не подключаемся к продовой БД напрямую во время разработки.
- Не заменяем существующие отчеты.
- Не строим декоративный dashboard.
- Не оцениваем звонки и мессенджеры, пока они не синхронизируются как надежные события.
- Не делаем универсальный конструктор правил до проверки текущего пульта на реальных локальных данных.

## Обрати внимание

Показатель `Задачи сегодня` основан на текущем состоянии задач. Для полностью честного контроля выполнения дня позже нужен отдельный снимок задач на начало дня.

Пульт уже можно использовать как операционный экран, но управленческие пороги SLA надо калибровать на реальных локальных данных перед продовым релизом.
